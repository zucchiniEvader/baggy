# Plugins and codemode

## MCP servers (`mcp`)

The user's MCP servers live in `mcp.json` in the data folder, in the format Claude Desktop, Cursor and Claude Code share: `{ "mcpServers": { "<name>": { … } } }` (VS Code's `servers` reads too). An entry is a command (`command`, `args`, `env`, `cwd`) or a remote server (`type: "http"`, `url`, `headers`, where `${VAR}` reads the environment), with `description`, `disabled`, and `timeout` (seconds, or milliseconds from 1000; ten minutes unset).

`mcp.Connect` speaks JSON-RPC 2.0, protocol `2025-06-18`, written from the spec (no SDK):

- **stdio**: the command starts with the environment (`mcp.Env`, the login shell's when set) plus its `env`; one JSON message per line; lines that are not JSON (a server's logs) are skipped; a request from the server is answered "method not found"; a cancelled call sends `notifications/cancelled`; stderr's last line explains an exit.
- **Streamable HTTP**: each message is a POST accepting JSON or an event stream (notifications before the response are passed to the client); `mcp-session-id` from `initialize` goes on every later request and a DELETE ends it; 401 and 403 say the server wants a sign-in, which for now means headers in `mcp.json` (OAuth sign-in is not built).

`initialize` (with the server's name and instructions, and whether its capabilities offer `resources`: `Client.HasResources`), `notifications/initialized`, `tools/list` (every page), `tools/call` (`content`, `structuredContent`, `isError`; with a context from `mcp.WithProgress` it sends a `_meta.progressToken` and passes the server's `notifications/progress` for it, over either transport, as `Progress` lines: "1/2 halfway"), and for a server with resources `resources/list` and `resources/templates/list` a page at a time (`cursor`, `nextCursor`; MCP Apps' `ui://` interfaces left out) and `resources/read` (`text`, or a base64 `blob`).

`mcp.Manager` keeps the file's servers by `ID` (the name lowercased, runs of other characters as `_`: `Fake Tools` → `fake_tools`). It reads the file again when it changes, connects a server on first use (a minute at most) and keeps it and its tool list, waits 30 seconds before trying a failed one again, and reconnects once when a call finds the connection broken. `Statuses` connects every server that is on; `Known` reports without connecting; `Call("<id>__<tool>", args)` runs one; `Lookup` finds a tool's declaration; `Resources`, `ResourceTemplates` and `ReadResource` reach a server's resources by its id, and a `Status` says whether it offers them.

Tested against a fake stdio server (the test binary) and an `httptest` Streamable HTTP server, and live against a server built on the official TypeScript SDK (1.30) over stdio and the reference `@modelcontextprotocol/server-everything` (seven resources, two templates, a document read).

## Codemode (`codemode`)

A bot uses plugins by writing a script, after pi's codemode: `codemode.Run(ctx, code, host, options)` runs JavaScript, the body of an async function, in a fresh goja VM with no timers, network, file system or modules. Its one way out is the host:

- `await tools.<name>(args)`: a tool by name. An unknown name rejects with the closest names. Calls run in parallel (eight at once by default; more than 1000 not yet awaited stop the script); each resolution runs on the VM's goroutine.
- `console.log` and `print` write the output; what the script returns is added after it (strings as they are, anything else as indented JSON).
- `searchTools(query)` ranks the tools by the words of the query, `describeTool(name)` gives one's declaration.
- `store(key, value)` and `load(key)` keep JSON values (1 MB each) for later scripts.
- A first line `// @options: {"max_output_tokens": …, "timeout_ms": …}` changes the budget (10,000 tokens by default, at most 50,000; the output keeps its start and end) or shortens the timeout (30 minutes by default). A timeout or Stop interrupts the VM wherever it stands.

A script that throws, times out, waits on a promise nothing will settle, or is stopped ends with the error after what it printed.

## In a turn (`team`)

With `Team.Plugins` (or `Team.Codemode`) set, every turn has the `codemode` tool. A script reaches the bot's file, search, shell and memory tools (argument checks and the turn's `BeforeToolCall`, so shell approval applies to a script's commands too) and every plugin tool as `tools.<server>__<tool>`, which resolves to `{content, structuredContent, isError}`. The model never gets plugin tools as tools of its own, so the tool list stays the same from turn to turn. While a script runs, its card shows what it has printed (`codemode.Options.Progress`, the last 4 KB) followed by the newest progress line of each plugin call still under way (`tools.github__search: 1/2 halfway`), reported with `tool.Update`. Values a script stores are kept per chat and bot (`store.ScriptSave`). When a ready server offers resources, the turn also has three tools of its own, named as Codex's and pi's: `list_mcp_resources { server?, cursor? }` and `list_mcp_resource_templates { server?, cursor? }` (every such server's first page as JSON without `server`; a cursor needs one) and `read_mcp_resource { server, uri }`, whose text comes back as text (at most 100,000 characters) and whose binary content (a picture too, since a tool result carries only text) is saved to a private temporary file the result names. They only read, so scripts and routine checks may call them. The system prompt's Plugins section lists each ready server with its description, whether it offers resources, and its tools (first description line, "reads only" for `readOnlyHint`), and says why a failed one is not available.

**Routine checks** (`Team.RunCheck`, which the desktop sets as `Team.Checks`): a routine's `check` runs as a script whose calls may only read: the bot's `read_file`, `find`, `grep` and `recall`, and plugin tools marked `readOnlyHint`; anything else fails the check. Five minutes at most; `store`/`load` reach the bot's DM's values, so a check keeps what it has seen and returns only what is new. A returned undefined, null, false, or empty string, list or object is a quiet check; anything else starts the run with it (at most 4,000 characters). See `routines.md`.

## The desktop

The Settings window's MCP Servers pane edits `mcp.json` in place, drilling down as Models does. Its first page is every server as a row (an icon tile, the name, how it stands: its number of tools and whether it offers resources, the error in red, Off, Not connected yet; a check or a red mark; a chevron) whose context menu has Edit…, Turn On or Turn Off and Delete, then Open mcp.json (written with no servers first when missing), Reconnect (reads the file again and connects every server in the background; the pane also checks them when it opens) and Add Server…. A server's page ("‹ MCP Servers / Name") has Connection (name, Kind: Command with its command, arguments one per line, environment as `KEY=value` lines and folder, or Remote (HTTP) with its URL and headers as `Name: value` lines) and Options (On, description, timeout in seconds), then its tools when it is connected; a bar under it has Delete (asked in an alert), Test Connection (connects and lists the tools, a minute at most: "Connected: 3 tools." or the error) and Save with Revert, or Cancel and Create. `mcp.SaveServer(path, old, server)` writes one entry, renamed when its name changed, refusing a name another entry has (or one with the same id) and an entry with neither a command nor a URL; it keeps the file's other entries and keys, the `servers` spelling when the file uses it, and the keys of the entry the editor does not know (`alwaysAllow`), and writes the whole file through a temporary one (mode 0600, since it holds keys). `mcp.DeleteServer` takes one out. The Manager sees the new file by its time and connects afresh. A command starts in its folder, `~` read as the home folder, or the home folder when it names none. A codemode card in the transcript shows the script's last lines.
